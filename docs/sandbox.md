# サンドボックス（人が作った C のコードを安全に動かす）の設計メモ

2026-11-22 にユーザーと相談して決めたこと。**まだ作っていない**（ユーザーの「まだ作るのは待って」）。作るときは、ここから始める。
作る前に、この設計をユーザーにもう一度見てもらう（基本設計にかかわる変更なので）。

## 1. 目的

- 誰かが作った C のコード（リモートの URL にあるものも）を、Monocs の上で直接動かしたい。
- 信用できないコードでも、OS・ファイル・ネットワーク・ハードウェアに手を出せないようにする。
- ブラウザと同じ考え方で、**できることを「画面に出す・キーとマウスを受ける」などに縛る**（ユーザーの案）。

## 2. 決めたこと（方式）

**EL0 で動かす ＋ 使える機能をしぼる**。ふつうのアプリは今までどおり EL1 で動かし、サンドボックスで動かすときだけの、別の道として足す。

- **なぜ EL0 か**: C はポインタで好きな番地を読み書きできるので、使える関数をしぼるだけでは守れない（`*(int *)0x3F200000 = 1` や OS のメモリの書き換え）。ブラウザの JavaScript は言語にポインタがないので関数をしぼるだけで済むが、C を安全に動かす WebAssembly も「メモリを閉じ込める」仕掛けとセット。
- **見送ったもの**:
  - 使える関数をしぼるだけ（事故は防げるが、悪意は防げない）。
  - コンパイラで読み書きのたびに確かめる（ソフトウェアでの閉じ込め。コンパイラが複雑になり、確かめの漏れが穴になる。1〜3 割遅い）。
  - Monocs の上の QEMU（Monocs の上では動かない: スレッド・fork・glib が要り、512MB に外と中が収まらず、とても遅い）。
  - EL2 のハイパーバイザー（サンドボックスより大きな設計の変更）。
- **基本方針への影響**: 単一の番地の空間・シングルタスク・ふつうのアプリ（EL1、OS の関数を直接呼ぶ、速さ、Linux との互換）は変わらない。「単一の特権」に、サンドボックスのときだけの例外が 1 つ入る。2 つの道を持ち続けることになる。

## 3. 仕組み

### 3.1 メモリ（仮想メモリは作らない）

- 恒等マップのまま。番地の付け替え・プロセスごとの番地の空間・スワップは作らない。
- MMU のページの許可（AP・UXN・PXN。今の表にもともとあるビット）だけを変える:
  - OS のメモリと周辺機器 → EL0 から触れない
  - サンドボックスの領域（データ・スタック・ヒープ）→ EL0 から読み書きできる、実行できない
  - サンドボックスのコード → EL0 から実行できる、書けない
  - OS のコード → EL0 から実行できない
- 同時に動くアプリは 1 つなので、入るときに領域のページの許可を変え、出るときに戻すだけ（TLB を消す）。領域は 2MB の境界にそろえて取ると、表を細かく分けずに済む。

### 3.2 使える機能（システムコール）

サンドボックスから OS を呼ぶのは `svc` 命令だけ。渡されたポインタは、すべてサンドボックスの領域の中を指しているかを確かめる
（数が少ないので確かめやすい）。ブラウザが「ページに許していること」と同じ考え方で、3 つに分ける（2026-11-22 にユーザーと決めた）。

**いつも許すもの（標準）**: 外に影響を出せないもの。

| 機能 | 理由 |
|---|---|
| 画面に書く、キーを読む（マウスも。curses と同じ形の入力）、画面の大きさ | ユーザーの案の出発点 |
| 時刻・眠る | 読むだけ・待つだけ |
| 乱数（`getentropy`） | 読むだけ |
| サンドボックスの中のメモリの確保 | 領域の中で完結する（中の C ライブラリが管理）。上限も決められる |
| 計算だけの関数（文字列・数学・並べ替え・正規表現・printf で文字列を作る） | 中で完結する（中の C ライブラリ） |
| 引数と、しぼった環境変数 | 渡すものをこちらで決める（パスワードなどは渡さない） |
| 終わる（終了の値） | 戻るだけ |

**ユーザーが許したときだけ使えるもの**: 動かすときに、ユーザーが許す（ブラウザの許可の確認と同じ）。

| 機能 | 条件 | ブラウザでいうと |
|---|---|---|
| ファイル | そのアプリ専用のフォルダの中だけ（例: `/var/lib/sandbox/<アプリ>/`）。量の上限。`..` は断る | ページごとの保存場所（localStorage など） |
| ユーザーが選んだファイルを読む | 起動のときにユーザーが渡すと決めたものだけ。読むだけ | ファイルを選ぶ画面 |
| ネットワーク | 取ってきた元のサーバーとだけ、HTTPS で。家の LAN（192.168.… など）には出させない | 同じ出どころの決まり |
| マルチコア（pthread） | 時間とコアの数の上限 | Web Worker |

**許さないもの**

- `system()`・ほかのプログラムを動かすこと（サンドボックスの外に出る）
- 好きなファイルを読み書き・消すこと
- GPIO などのハードウェア（つないだ部品を壊したり、ショートさせたりしうる。ピンごとに許す形も作れるが、物を壊す危なさは残る）
- SD カードを直接、再起動、Wi-Fi・パスワードの設定、サービスの操作、ほかのコアの操作

最初に作るのは「いつも許すもの」だけにして、許可の仕組み（2 つ目の表）は後から足す。

### 3.3 コンパイラ（1 つのまま）

- slimcc は 1 つのまま。EL0 の守りは CPU がするので、出す機械語はふつうのアプリと同じ。
- 足すのは、サンドボックス用のオプション 1 つ: キャッシュのキーに印を入れる。インラインアセンブリは、断らなくてよい（2026-11-26 に見直し: EL0 では特権の命令は CPU が止めるので、書かれても外には出られない。sbtest の「特権の命令」で確かめた）。
- 変わるのは**つなぐところ**: OS の関数表（`os/api/api.def`）の代わりに、サンドボックス用の小さな表（システムコールの入口と、中の C ライブラリ）につなぐ。

- **コンパイラの中身は変えない**（2026-11-22 に確かめた）: 構文解析・最適化・機械語を作るところはそのまま。守りを CPU がするので、
  読み書きのたびに確かめる命令などは足さない（見送ったソフトウェアでの閉じ込めなら、コード生成・関数ポインタの飛び先・
  レジスタの決まりまで手が入った）。複雑さはコンパイラの外（表、中の C ライブラリ、システムコールの入口）に収める。
- **コンパイラが自分で呼ぶ部品も、サンドボックスの表に入れる**: slimcc は、構造体のコピー・0 埋めで `memcpy`・`memset`、
  `long double` の計算で `__addtf3` など（cc/rt/softfp128.c）、大きな整数で `__slimcc_bitint_*`、`__clear_cache` を自分で呼ぶ。
  今は OS の関数表から取っているので、サンドボックスの中の C ライブラリにも入れる（どれも計算だけで安全）。`-fopenmp` の
  `__monocs_omp_*` は pthread が要るので、最初は渡さない（3.2 の「ユーザーが許したときだけ」）。
- **スレッドの変数（errno など）**: コンパイラが出す `mrs …, tpidr_el0` は EL0 でも使える。つなぐときに `tls:errno` などを
  サンドボックスの中の TLS の場所に向ける（今の run.c の resolve と同じ形で、向け先だけ変える）。
- **システムコールの入口**: `svc` を出す小さな関数は、信頼できる側のライブラリにインラインアセンブリで書く（インラインアセンブリを
  断るのは、サンドボックスのアプリのソースだけ）。

### 3.4 中で使う C ライブラリ（いちばん手間がかかる）

- 今の picolibc は OS の中にあって OS のメモリ（errno の TLS、stdio の FILE、malloc）を使うので、EL0 からはそのまま呼べない。
- 文字列・printf（書く先はシステムコール）・数学の関数・malloc（領域の中）と、curses の画面の部分を、サンドボックスの中に別に入れる。同じ slimcc で作り、共有のライブラリと同じくキャッシュする。

### 3.5 止める・後始末

- 時間の上限（今の `timeout` の仕組み）、メモリの上限（領域の大きさ）。
- 例外（EL0 からの不正なアクセス）なら、そのアプリだけ止める（今と同じ）。

## 4. キャッシュ

- 今の仕組み（`/var/cache/slimcc`、キーはソースの絶対パスとオプション、使えるかは読んだファイルの大きさ・日時・中身で確かめる）をそのまま使う。キーにサンドボックスの印を入れて、ふつうのアプリの結果と混ぜない。つないだ結果の覚え（メモリの写し）も分ける。
- キャッシュはサンドボックスからは触れない（ファイルの機能を渡さない）。書くのはいつも OS。

## 5. リモートのコード（`run URL`）

### 5.0 取ってくる道（プロトコル）

2026-11-22 にユーザーと決めた: **最初は HTTP ＋ハッシュ**。

- **最初に作るもの**: `run http://…/prog.c#sha256=…`。取ってくるのは今の `curl` の仕組み、相手の側は今の `httpd`（Monocs 同士なら
  新しく作るものはない）。足すのは、URL の `#sha256=` と、取ってきた中身のハッシュを確かめて合わなければ動かさないところだけ。
- **なぜ HTTP でよいか**: ハッシュが合わなければ動かさないので、途中で 1 バイトでも書き換えられれば必ず気づける（apt や Go のモジュールも、
  取ってくる道は HTTP でよい代わりに、中身をハッシュ・署名で確かめる）。暗号の計算がなく軽い。中身が本物でも悪いコードだったときは、
  サンドボックスが守る。
- **条件 1: ハッシュは別の道で受け取る**。コードと同じ HTTP でハッシュも取ってくるのでは、両方すり替えられるので意味がない。
  作った人から別の道（チャットなど。相手の Monocs で `sha256sum` を出してもらう）で受け取る。
- **条件 2: ハッシュがないとき**は、1 回目に取った中身のハッシュを覚え（5.2）、2 回目から変わっていないかを確かめる（1 回目は守れない）。
  そのときは標準のサンドボックス（許可なし）で動かす。ファイル・ネットワークなどを許すのは、ハッシュで確かめたものだけにする
  （すり替えられたコードに許可ごと渡さないため）。
- **守れないこと**: 中身を見られること（HTTPS でも、ハッシュを教えてくれた相手のコード自体が悪いことは防げない）。
- **後から足すもの**:
  - **HTTPS**: 人が公開したコード（GitHub・Web）を取るとき。Monocs には `curl` と TLS のライブラリがもうあるので、`run https://…` も
    同じ道で使える（ハッシュがあればそれも確かめる）。ただし Monocs の `httpd` は HTTPS のサーバーではない（Monocs 同士には使えない）。
  - **sftp**: Monocs 同士で、鍵で相手を確かめて暗号化してやりとりしたくなったとき。サーバー（sshd）はどの Monocs にもあるが、
    クライアントを作る必要がある（sshd の部品を使い回す。相手のホスト鍵を覚える known_hosts、自分の鍵の署名、sftp の要求を送る側）。

| | sftp | HTTPS | HTTP ＋ハッシュ |
|---|---|---|---|
| Monocs の今 | サーバーはある、クライアントはない | クライアントはある、サーバーはない | どちらもある |
| 向いている相手 | Monocs 同士・自分の機械 | 人が公開したコード | Monocs 同士（ハッシュを別の道で受け取れるとき） |
| すり替えへの守り | 暗号化と相手のホスト鍵 | 暗号化と証明書 | ハッシュ |
| 速さ | 暗号の計算あり（Monocs で 2〜3MB/s） | 暗号の計算あり（つなぎ始めに約 0.7 秒） | 速い（C のソースならどれも 1 秒もかからない） |

### 5.1 置き場所

- 取ってきたものは `/var/cache/sandbox/<URL のフォルダの部分のハッシュ>/` に置き、その中に元の URL を書いた `url.txt` を置く。
  - ハッシュ（小文字の 16 進）にするのは、FAT32 が大文字と小文字を区別しないため（リモートの `a.c` と `A.c` が同じ場所にならないように）と、名前に使えない文字（`:` `?` `*` `"` `<` `>` `|`）を避けるため。
  - フォルダの中のファイル名は URL のまま（使えない文字はパーセントエンコードに置き換える）。同じフォルダの `#include "x.h"` も隣に置けば、今の探し方で見つかる。
  - `..` を含む URL は断る（どのファイルシステムでも要る守り）。
- 同じ URL は同じ場所なので、作者が直したら同じ場所に書き直され、増え続けない。`cache` で URL の一覧を出し、`cache clear URL` で消す。
- FAT32 のままでよい（ファイルシステムを変えても `..` の断りと `/` の置き換えは要り、PC で中身を見られなくなる。2026-11-22 にユーザーと合意）。

### 5.2 信頼（許した版と同じか）

- 一度許したときの中身の SHA-256 を覚え、次に取ってきて中身が変わっていたら「前に許した版から変わっています。動かしますか？」と聞く（ssh が初めての相手の鍵を覚えるのと同じ考え方）。`run URL#sha256=…` で固定もできるようにする。
- **日時ではだめ**: サーバーが返す日時（Last-Modified）は相手が好きに決められ、手元の日時は取ってきた時刻なので、中身が同じかはわからない。
- コンパイルのキャッシュを使ってよいかは、ふつうのアプリと同じく大きさと日時でよい（SD カードに書くのは Monocs 自身なので）。

| 目的 | 使うもの | いつ計算するか |
|---|---|---|
| コンパイルのキャッシュを使ってよいか | 大きさと日時 | 毎回（軽い） |
| 前に許したコードと同じか | 中身の SHA-256 | 新しく取ってきたときだけ |

- 重さ: ソースは数 KB〜数百 KB、SHA-256 は実機でも 1 秒に数十 MB くらいの見込み（測っていない）で、ネットワークの時間に比べて小さい。作者が直したかを見に行くときは `If-None-Match`・`If-Modified-Since` を使えば、変わっていなければ中身は送られてこない。

## 6. 信頼を判断しやすくする手順（サンドボックスとは別に、作れるもの）

1. **出どころを確かめる**: 作者が公開したハッシュや署名と照らす（署名の確かめは BearSSL で作れる）。
2. **何をするプログラムかを一覧にする**（`cc --report` の案）: つなぐときに使う OS の関数がわかるので、種類ごとに並べる（ファイルを消す、ネットワーク、`system()`、SD カードを直接、再起動）。インラインアセンブリと周辺機器の番地（0x3F…）の直書きも知らせる。いちばん小さくて効く。悪意のある手（ポインタで OS のメモリを直接）は一覧に出ないので、これだけでは悪意は防げない。
3. **使い捨ての場所で試す**: Pi 5 の QEMU で、SD カードのイメージの写しを使って動かす（何をされても写しを捨てるだけ）。
4. **読んで確かめる**: 人か Claude が、2 の一覧で気になったところを重点的に。

## 7. 気をつけること

- **コンパイラ自身が攻められる口になる**: 信用できないソースをコンパイルするのは EL1 のコンパイラ。わざと作った変なソースでコンパイラを暴走させられると、サンドボックスの外で悪さをされる。最初は壊れたソース・乱数のソースをたくさん食べさせて落ちないことを確かめる（Makefile の解釈器では 2,000 通りでやった）。本当に知らない人のコードを動かすなら、コンパイラ自身も EL0 で動かすことを考える（手間が大きい）。
- サンドボックスの中では使える関数が少ないので、Linux のソフトがそのまま動く、とはならない（画面のゲーム・デモなどが向く）。

## 8. 作る順の案

1. `cc --report`（6 の 2。小さく、サンドボックスがなくても役に立つ）… **済み（2026-11-26）**: os/slimcc/report.c。つなぐとき（run.c の resolve）に OS の表から引いた名前を覚えて種類ごとに並べ、渡したソースのファイル（ヘッダーは見ない）から注釈・文字列を除いてインラインアセンブリと周辺機器の番地（0x3F000000〜0x40FFFFFF）を探す。-l のハードウェアのライブラリ（gpio・i2c・spi・pwm・softuart）も知らせる
2. MMU の EL0 の許可と、EL0 から戻る例外の道（何もしないプログラムを EL0 で動かして戻る）… **済み（2026-11-26）**: os/kernel/sandbox.c の sandbox_run（コード 2MB・データとスタック 2MB の 2MB のブロックを mmu_sandbox_map で EL0 から使える形にし、sandbox_eret で入る）。RAM 全部に UXN を足した（前は EL0 から OS のコードを実行できる設定だった）。vectors.S の ventry_lower が SP_EL0（フレームの sp0）と TPIDR_EL0（sandbox_user_tp・sandbox_kernel_tp）を入れ替える。svc #0（終わる）・不正なアクセス・Ctrl-C・時間の上限で longjmp で戻る。開発用のコマンド `sbtest`（9 項目。QEMU と実機で全部 ok。ふつうのアプリの速さは同じ: primes 44ms）
3. システムコールの入口（画面に書く・終わる）と、中の C ライブラリの最小（文字列・printf）… **済み（2026-11-26）**: シェルの `sandbox FILE.c [引数]`（os/slimcc/sandbox_cmd.c）。FILE.c と /usr/lib/sandbox/*.c（lib/sandbox: start.c の __sandbox_start、stdio.c の printf 一族・puts・fputc など（書式は d i u x X o c s p f e g と印・幅・精度・長さ）、string.c、stdlib.c の malloc（空きの一覧の簡単なもの）・exit など）を毎回コンパイルし、OS の関数にはつながずに（足りない関数は undefined symbol）サンドボックスの領域の中でつなぐ（cc/memlink.c の確保を領域の頭に向ける）。領域はプログラム 4MB（EL0 が読み書き・実行。データも中にあるため）・データ 8MB（頭に引数、ヒープ、上の 1MB がスタック）。システムコールは svc #0 と x8 の番号（Linux と同じ形）: 0 終わる、1 書く（fd 1・2、ポインタは領域の中か確かめる）。QEMU と実機で、書式・引数・malloc・構造体のコピー・stderr・終了の値、fopen が undefined symbol、OS のメモリと GPIO への書き込みが止まる（139）。まだ: キャッシュ（毎回 0.4 秒ほどコンパイル）、キー・マウス・画面の大きさ・時刻・眠る・乱数（4）
4. キー・マウス・画面の大きさ・時刻・眠る・乱数、curses の画面の部分（3.2 の「いつも許すもの」がそろう）
5. `run URL`: まず HTTP ＋ハッシュ（5.0。`#sha256=`、置き場所、許した版のハッシュ、`If-None-Match`）。HTTPS・sftp は後から
6. コンパイラに壊れたソースを食べさせる試験
7. ユーザーが許したときだけ使えるもの（専用フォルダのファイル、元のサーバーとのネットワークなど）と、許可の確かめ

# 12. OS の中身

作りを忘れたとき・直したいときのための章です。細かい経緯と測った数字は `CLAUDE.md` にあります。

## 12.1 設計の柱

| 柱 | 中身 |
|---|---|
| 単一アドレス空間・単一特権 | OS もアプリも EL1。MMU は恒等マップ（番地 = 物理番地）で、キャッシュを効かせるためと、守り（下）のために使う |
| シングルタスク | 同時に動くアプリは 1 つ。スレッドのスケジューラはない |
| コアの使い分け | コア 0: シェルとアプリ。コア 1・2: アプリが借りる（コンパイルの分担、pthread、`monocs_core_start`）。コア 3: サービス |
| OS の関数は表で渡す | アプリは OS の関数を直接呼ぶ。コンパイルの結果は名前のまま持ち、動かすときに「名前 → 番地」の表（`os/api/api.def`）でつなぐ |
| ソースのまま動かす | コンパイラとリンカをカーネルに組み込み、動かすたびにコンパイル（キャッシュあり）してメモリ上でつなぐ |
| ドライバは最小限 | カーネルに入れるのは起動に要るもの（UART・USB・SD・タイマー・割り込み・メールボックス・LED）と、例外として Wi-Fi。部品のドライバは `/usr/lib` のライブラリ |

## 12.2 起動の順番

1. **GPU のファームウェア**（`bootcode.bin`・`start.elf`）が `config.txt` を読み、`/boot/kernel8.img` を 0x80000 に置く。
   コア 1〜3 はスピンテーブル（0xD8 + 8n 番地）で待たせる。
2. **`os/boot/boot.S`**: コア 0 以外を待たせ、EL2 から EL1 に降り、FP/SIMD を使えるようにし、スタックを決め、BSS を 0 にして `kernel_main` へ。
3. **`os/kernel/main.c` の `kernel_main`**: UART → LED → 例外のベクタ → MMU → TLS（コアごとの変数）→ メモリ → 割り込み → タイマー →
   試しの起動の確かめ（tryboot）→ ウォッチドッグ → USB・ネットワーク → コア 1〜3 を起こす → SD カードをマウント → シェル。
4. **`os/shell/shell.c` の `shell_main`**: `/tmp` を空にし、`/root/.profile` を動かし、時刻を `/etc/fake-hwclock.data` から読み、
   サービスを始め（`/etc/services.txt`）、`/autorun.c` があれば動かして、プロンプトを出す。

## 12.3 メモリの配置

```
0x00000000  0 番地のページ（無効。NULL の参照を捕まえる）
0x000000D8  ファームウェアのスピンテーブル（コア 1〜3 の飛び先）
0x00060000  カーネルの記録の輪（再起動をまたいで残す。0x60000〜0x70020）
0x00080000  カーネル: .text・.rodata（読み出し専用）、.data、.bss
            コア 0 のスタック 8MB、コア 1〜3 のスタック 8MB × 3（いちばん下の 64KB はガードページ）
            コアごとの TLS 1MB × 4
   …        ヒープ（約 400MB）: 下からカーネル用、上からアプリ用に広げる（どちらも TLSF）
0x1C000000  GPU 用のメモリ（64MB。使っていない）
0x3F000000  周辺機器（GPIO 0x3F200000、UART 0x3F201000、システムタイマー 0x3F003000、メールボックス 0x3F00B880 …）
0x40000000  ARM ローカルの周辺（コアごとのタイマー・割り込み・メールボックス）
```

- RAM は 2MB のブロックで、ライトバックのキャッシュ。カーネルのコードとスタックのガードのところだけ 4KB のページに分ける。
- **アプリ用のヒープ**: アプリの実行中の malloc はアプリ用から取り、アプリが終わったら丸ごと捨てる（free しなかった分も戻る）。
  ファイルのキャッシュなど、アプリが終わっても残すものはカーネル用から取る。

## 12.4 例外と守り

- 例外のベクタ（`os/kernel/vectors.S`）でレジスタを退避し、`os/kernel/exception.c` で振り分ける。
- アプリ（とアプリが借りたコア）で同期例外が起きたら、内容を出して、`setjmp` で覚えたシェルの戻り先に `longjmp` する
  （`os/kernel/app.c` の `app_call`）。そのとき、開いたファイル・ソケットを閉じ、ほかのコアの仕事を止め、ヒープを捨てる。
- カーネルのコードへの書き込みは、ページが読み出し専用なので例外になる。
- スタックがガードページに入ったら、ベクタの入口で気づき、コアごとの非常用のスタックに切り替えて止める。
- 守るのはバグからだけ。アプリも EL1 なので、わざと MMU を書き換えれば外せる。

## 12.5 メモリの守り（仮想メモリはない）

MMU は使っていますが、番地と物理番地が同じ（恒等マップ）です。プロセスごとの別の番地の空間も、スワップもありません。
ページの設定で、よくある事故だけを捕まえます（`os/kernel/mmu.c`）。

| 事故 | どう捕まえるか |
|---|---|
| NULL の参照 | 0 番地のページを無効にしてあるので、読んでも書いても例外になる |
| OS のコードを書き換える | カーネルのコードと定数（.text・.rodata）のページを読み出し専用にしてある |
| スタックのあふれ | 各コアのスタックのいちばん下の 64KB を無効なページ（ガードページ）にしてある。入ったら非常用のスタックに切り替えて止める |

どれも、アプリだけを止めて、止まった関数を出してシェルに戻ります。OS とサービスはそのまま動き続けます。

守りではありませんが、事故に気づきやすくしているものもあります。

- アプリのヒープは OS のヒープと分けてあり、アプリが終わったら丸ごと捨てて 0 で塗ります。OS が捨てられたメモリを使うと NULL を読むことになり、すぐ例外で気づけます。
- どちらのヒープのものでもない番地を `free` すると、「free: invalid pointer」と出して無視します。

守っていないもの:

- **OS のデータ（変数・ヒープ）**: アプリから書き換えられます（同じ特権・同じ番地の空間なので）。
- **64KB を飛び越える大きな局所変数**: ガードページを飛び越えると、スタックのあふれとして捕まえられません。
- **わざと外すこと**: アプリも EL1 なので、MMU の設定を書き換えれば守りを外せます。
- 4KB のページに分ける表は 12 個まで（`L3_POOL`）。カーネルが大きくなって足りなくなると、残りは守られません。

つまり、Monocs の守りは**バグから守るためのもの**で、悪意のあるプログラムからは守れません。これは設計の結果で、
その分アプリは OS の関数やハードウェアを直接、速く使えます。

## 12.6 システムコールはない（OS の関数を直接呼ぶ）

Linux では、アプリは `svc` 命令で OS に頼みます。そのたびに特権の段が変わり（EL0 → EL1）、レジスタの退避と引数の確かめが入ります。

Monocs では、アプリも OS も同じ EL1 で動くので、**OS の関数をふつうの関数として直接呼びます**。

- アプリが `printf` や `open` を呼ぶと、そのままカーネルの中の C の関数に飛びます。`open`・`read`・`write` のように、
  Linux ではシステムコールの名前の関数も、Monocs ではふつうの関数です。
- 番地は、アプリを動かすときにつなぎます。コンパイルの結果は OS の関数を名前のまま持っていて、動かすたびに
  OS の関数表（`os/api/api.def`、約 840 個）で「名前 → 番地」を引いて埋めます（`cc/memlink.c`）。そのため、カーネルを
  入れ替えてもアプリを作り直さずに済みます。表にない関数を呼ぶと、動かすときに `undefined symbol` になります。
- アプリから呼べる関数を増やすときは、`api.def` に足します。
- 考え方は、昔の RISC OS の SWI（関数の表を通して OS を呼ぶ）に近いものです。

良いところは、呼ぶ手間がふつうの関数呼び出しと同じこと（`read` や GPIO の読み書きを細かく何度も呼んでも遅くならない）と、
仕組みがとても簡単なことです。引き換えに、OS とアプリの間に壁がありません（上の 12.5）。

## 12.7 マルチコアとロック

- `os/kernel/smp.c`: コア 1〜3 に関数を渡して動かす（`smp_run`・`smp_wait`）。止めるときはメールボックスの割り込みで知らせる。
- ロック（`os/kernel/lock.c`）: ldaxr・stlxr のスピンロック（LSE のアトミック命令は A53 にない）。OS のロックを持っている間は、
  そのコアの中断（Ctrl-C など）を後回しにする。1 つのロックはキャッシュライン 1 本（偽の共有を避ける）。
- C ライブラリ（picolibc）の errno などの状態は、コアごとの TLS（`_Thread_local`）。コンパイラの状態もコアごとなので、3 コアで同時にコンパイルできる。
- 待つ間は `wfi`（コア 0）・`wfe`（ほか）で眠る。

## 12.8 コンソール

- 入力: UART・USB シリアルの割り込みで受けた文字は 1 つの受信バッファに入る。telnet・ssh の文字もサービスからそこに入る。
- 出力: UART の送信バッファに入れ、割り込みで送る。同じものを USB シリアルと「コンソールの写し」（`os/kernel/contap.c`。telnet・ssh のサービスが読む）にも送る。
- `ssh monocs 'コマンド'` は別の道（`os/kernel/rexec.c`）で、シェルがプロンプトで待つ間に行を受け取り、出力を ssh の輪に向けて動かす。
- 端末の設定（termios）は Linux と同じ（`os/libc/termios.c`）。

## 12.9 ファイルシステム

```
アプリ（open・read・fopen …）
  → VFS（os/fs/vfs.c）        fd の表、ファイルのキャッシュ、ないパスの覚え、/dev/null、ソケット・パイプへの振り分け
  → FatFs（third_party）      FAT32
  → diskio（os/fs/diskio.c）  書き込みのまとめ（ライトバック）、先読み、セクタのキャッシュ
  → sd.c → sdhost.c           SD カードのドライバ（SDHOST、50MHz、PIO）。失敗したら sd_emmc.c
```

- FatFs を呼ぶのは VFS のロック（`vfs_lock`）の中だけ。キャッシュに当たるものは別のロック（`vfs_fc_lock`）だけで答え、SD カードを待たない。
- SD カードの EMMC のコントローラは、Wi-Fi のチップ（SDIO）に使っている。

## 12.10 ネットワーク

- lwIP（`third_party/lwip`）は、1 つのロック（`net_lock`。割り込みを止めて取る）の中からだけ呼ぶ（NO_SYS、raw API）。呼ぶのは受信の割り込み、10ms ごとのタイマー割り込み、送信。
- 口は 2 つ: USB イーサネット（`os/drivers/usb.c` の CDC-ECM）と Wi-Fi（`os/drivers/sdio.c`・`wifi.c`。チップは CYW43436s、ファームウェアは `/usr/lib/firmware/brcm`）。
- アプリ向け: `os/net/tcp_api.c`・`udp_api.c`・`dns_api.c`（Monocs の API）、その上に `os/libc/socket.c`・`select.c`・`netdb.c`（Linux と同じソケット）。

## 12.11 プログラムを動かす仕組み

```
run hello.c / 名前 / make
  → os/slimcc/run.c       ファイルを集める（フォルダ、Makefile、compile_flags.txt、-l のライブラリ）
  → os/slimcc/cache.c     キャッシュを使えるか（読んだファイルの大きさ・日時・中身のハッシュ）
  → cc/（libslimcc）      前処理 → 構文解析 → 中間表現（SSA）と最適化 → 機械語（内蔵アセンブラ）。3 コアで分担
  → cc/memlink.c          メモリ上でつなぐ。OS の関数は api.def の表で解決
  → os/kernel/app.c       app_call で main を呼ぶ（終わり・例外・Ctrl-C でここに戻る）
```

- コンパイルの結果（オブジェクト）は、OS の番地を含まない形でキャッシュする。カーネルを入れ替えても使える（コンパイラが変わったら作り直す）。
- 2 回目からは、つないだ後のメモリの写しも覚えておき、そのまま戻して動かす（大きなプログラムの起動が速い）。
- `system()` は、子のアプリを親の中で入れ子に動かす（8 段まで）。
- Makefile は `os/slimcc/makefile.c` が GNU make と同じように読む（コマンドは動かさない）。

## 12.12 サービス

`os/kernel/svc.c`: コア 3 で、すべてのサービスの `service_poll` を順に呼び続ける。どれも仕事をしなければ `wfe` で眠る
（タイマーのイベントで約 1ms ごとに起きる）。ファイル・ソケットには持ち主（サービスの番号）を付け、止めたときに閉じる。

## 12.13 守りと記録

- ウォッチドッグ（`os/kernel/watchdog.c`）: コア 0 のタイマー割り込みが餌をやる。止まると約 16 秒でリセット。
- 試しの起動（`os/kernel/tryboot.c`）: コマンドラインに `monocs.tryboot` があれば、90 秒以内に確かめられなければ餌をやめる。
- 記録（`os/kernel/klog.c`・`klog_file.c`）: 64KB の輪。固定の番地にあり、再起動をまたいで残る。SD カードの `/var/log` にも書く。

## 12.14 コンパイラ slimcc-a64

- 元は slimcc（C11 のコンパイラ、MIT。`cc/UPSTREAM.md`）。AArch64 向けに作り直し、`cc/` で直接直している。
- C23、SSA の中間表現（`cc/ir.inc`。AArch64 のレジスタ・呼び出し規約は `cc/ir_a64.inc`、命令を出すところは `cc/ir_a64_emit.inc`。別の CPU を足すときの手がかりは `docs/slimcc-codegen.md` の 0.1）、インライン展開、ループの最適化、Cortex-A53 向けの命令の並べ替え（`cc/sched.inc`）、strict aliasing、OpenMP（`cc/omp.inc`）。
- 内蔵アセンブラ（`cc/assembler.c`）とリンカ slimld（`cc/ld.c`）。どちらも GNU as・ld と同じ結果になることを確かめている。
- 分岐を減らす変形（csel・ccmp・tbz・cset）、switch の表引きとビットの表、呼び出しのある関数でも x0〜x7 を値に使うレジスタの割り当て（2026-11-27）。
- 出すコードは GCC -O2 と比べて、整数・文字列の計算で約 1.02 倍、浮動小数点の計算で約 1.3 倍、カーネルの中のコンパイラで約 1.3 倍遅い（2026-11-27）。縮める作業の手引きは `docs/slimcc-codegen.md`。

## 12.15 ソースの場所

| フォルダ | 中身 |
|---|---|
| `os/boot/` | 起動のアセンブリ、リンカのスクリプト、config.txt |
| `os/kernel/` | 例外、MMU、メモリ、マルチコア、ロック、TLS、アプリの実行、サービス、時計、記録、ウォッチドッグ、性能カウンタ |
| `os/drivers/` | uart、usb、sd（sdhost・sd_emmc）、sdio・wifi、timer、irq、mailbox、led、rng |
| `os/fs/` | VFS、FatFs のつなぎ込み、SD カードの読み書きのまとめ |
| `os/net/` | lwIP のつなぎ込み、TCP・UDP・DNS の API |
| `os/libc/` | C ライブラリのつなぎ込み、malloc（TLSF）、POSIX の補い、ソケット、pthread、OpenMP、シグナル、termios など |
| `os/slimcc/` | 組み込みのコンパイラの呼び出し（run、cc、キャッシュ、Makefile） |
| `os/api/` | OS の関数表（`api.def`）と、アプリ用のヘッダー（`include/`） |
| `os/shell/` | シェル、行の編集、perf、wifi コマンド |
| `os/curses/` | curses（ncurses 互換の小さなもの） |
| `cc/` | slimcc-a64（コンパイラ・アセンブラ・リンカ） |
| `bin/`・`services/`・`lib/`・`samples/` | SD カードの `/usr/bin`・`/usr/sbin`・`/usr/lib`・`/usr/share/samples` に入るもの |
| `third_party/` | picolibc、FatFs、lwIP、BearSSL、slimcc（元のもの）、Wi-Fi のファームウェア（どれも無改造） |
| `tools/` | Pi 5 で使う道具（nos.py、試験、SD カードのイメージ作り、セルフホスト） |

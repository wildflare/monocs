# 6. プログラムを作って動かす

Monocs の中にはコンパイラ（slimcc-a64）が入っていて、**C のソースをその場でコンパイルして動かします**。Pi 5 は要りません。
詳しい書き方・使える関数・落とし穴は `docs/programming-guide.md` にあります。この章はその入口です。

## 6.1 動かし方は 4 つ

| やり方 | 例 | 向いていること |
|---|---|---|
| `run` | `run hello.c a b`、`run DIR`、`run -` | ちょっと書いてすぐ試す |
| 名前で動かす | `/root/apps/hello.c` を置いて `hello a b` | 自分のコマンドとして使う |
| `make` | `make`、`make posix` | Linux の Makefile のあるソースを置く |
| `cc -o` | `cc -o hello hello.c && ./hello` | 実行ファイルを作る（Linux と同じ） |

どの場合も、**2 回目からはコンパイルの結果のキャッシュ**（`/var/cache/slimcc`）を使うので、読み込むだけで動きます。（詳しくは 6.8）
ソースや読んだヘッダーを書き換えると、変わったファイルだけコンパイルし直します。

### run

```sh
run hello.c 引数…            # .c は省ける（run hello）
run -std=c17 -DDEBUG -lgpio prog.c   # オプションはファイルの前に
run /root/apps/mi file.txt   # フォルダなら中の .c（と Makefile）を全部まとめて
run -                        # キーボードから打った C（. だけの行か Ctrl-D で終わり）
```

ファイルは作りません（`tcc -run` と同じ使い方）。

### 名前で動かす

`PATH`（`/root/apps:/usr/bin`）にあるものは名前だけで動きます。

- `/root/apps/名前.c`（1 つのファイル）か、`/root/apps/名前/`（フォルダ。中の .c、Makefile、compile_flags.txt）。
- 付いてくるコマンド（`/usr/bin/ls.c` など）も同じ仕組みで、ソースのまま動いています。

### make

フォルダに Linux の `Makefile` があれば、それを読んでコンパイルするファイルとオプションを決めます（Makefile のコマンドは動かしません）。

```sh
cd /root/apps/lua
make posix               # 目標・変数を選ぶ（選んだものはフォルダの .monocs-make に覚える）
lua                      # 名前で動かす（選んだ作り方で）
make clean               # 選んだ作り方を消す
make hello               # Makefile がなければ hello.c をコンパイルするだけ
```

`make` はコンパイルして誤りを見て、キャッシュに入れるだけで、**実行ファイルは作りません**。動かすのは名前か `./prog` です。

### cc

```sh
cc -o prog a.c b.c -lgpio      # 実行ファイル（Monocs 独自の形。./prog で動く）
cc -c x.c -o x.o               # .o（Monocs のカーネルを作るときに使う）
```

`-std=`、`-D`、`-U`、`-I`、`-l名前`、`-fopenmp`、`-include` が効きます。`-O2`・`-Wall`・`-g` などは黙って読み捨てます。
実行ファイルはソースを直しても古いままなので、作り直してください。

## 6.2 どのフォルダで作るか

試作は **`/root` の下に自分用のフォルダを作って**やります（`/root` はホームで、Monocs の更新でも触られません）。

```sh
mkdir -p /root/work      # 名前は何でもよい（proto、src など）
cd /root/work
mi test.c
run test.c               # その場でコンパイルして動かす
```

まとまって、名前だけで呼べるコマンドにしたくなったら `/root/apps` に移します。

```sh
mv /root/work/hello.c /root/apps/     # どこからでも hello で動く
```

| フォルダ | 向いていること | 気をつけること |
|---|---|---|
| `/root/work` など（自分で作る） | 試作、試し書き | PATH にないので `run`・`./prog` で動かす |
| `/root/apps` | 名前で呼ぶ自分のコマンド | ここに置いた `.c` やフォルダは全部コマンドの名前になる（試作を置くと Tab の補完などに混ざる） |
| `/tmp` | 一度きりの作業 | **起動のたびに空になる** |
| `/usr` の下 | 置かない | Monocs の更新で入れ替わる |

Pi 5 のエディタで書きたいときは、`sshfs monocs:/ ~/monocs` でつなぐと、`~/monocs/root/work` を PC のフォルダのように開けます。

## 6.3 最初のプログラム

```c
#include <stdio.h>

int main(int argc, char **argv)
{
    printf("Hello, Monocs!\n");
    for (int i = 0; i < argc; i++)
        printf("argv[%d] = %s\n", i, argv[i]);
    return 0;
}
```

Monocs のエディタ `mi` で書いて（`mi /root/apps/hello.c`）、`hello a b` で動かします。Pi 5 で書いたものなら
`python3 tools/uart/nos.py run hello.c a b`（送って、作って、動かす）。

## 6.4 知っておくこと

- **既定の規格は gnu23**（C23 と GNU の拡張）。宣言していない関数を呼ぶとエラーです（警告ではない）。
- **使える関数は OS の関数表（`os/api/api.def`、約 840 個）にあるものだけ**です。ないものは動かすときに
  `link error: undefined symbol 'fork'` のようになります。
- 同時に動くのは 1 つ。`fork`・`exec` はありませんが、`system()`・`popen()` は使えます（入れ子に動く）。
- **アプリが終わると OS が後始末をします**: 開いたファイル・ソケットを閉じ、malloc したメモリは free しなかった分もまとめて捨てます。
- static の変数は、動かすたびに初期値から始まります。
- キー入力は Linux の端末と同じです（Enter で 1 行ずつ。1 文字ずつ読むなら `tcsetattr` で ICANON を外す）。
- NULL の参照・スタックのあふれ・OS のコードへの書き込みは例外で止まり、どの関数で止まったかを出してシェルに戻ります。

## 6.5 共有のライブラリ

`/usr/lib/名前/` に C のソースのまま置いてあり、`-l名前` を付けると一緒にコンパイルして入れます。

| ライブラリ | 中身 |
|---|---|
| `-lgpio` | GPIO（[第 9 章](09-hardware.md)） |
| `-li2c`、`-lspi`、`-lsoftuart`、`-lpwm` | I2C、SPI、ソフトウェアの UART、PWM |
| `-ltls` | TLS（HTTPS）でつなぐ（中身は BearSSL） |
| `-linflate` | gzip・zlib の展開 |

`-l名前` を付け忘れてライブラリのヘッダー（`monocs_pwm.h` など）を `#include` すると、「file not found」の下に
`note: monocs_pwm.h is in the library /usr/lib/pwm; add -lpwm …` と案内が出ます（勝手にはつなぎません。Linux の gcc と同じ動きにするため）。

自分で作るときは、`/usr/lib/名前/` に .c と .h、オプションがあれば `compile_flags.txt`（1 行に 1 つ）、入れたくないファイルは `.runignore` に書きます。

## 6.6 マルチコア

- **pthread**: スレッド 1 つに空いたコアを 1 つまるごと渡します。サービスがあるとアプリのコアは 3 つなので、作れるスレッドは 2 つまで（足りなければ `EAGAIN`）。
- **OpenMP**: `-fopenmp`。`#pragma omp parallel for` などが使えます。
- **Monocs の関数**: `monocs_core_start(コア, 関数, 引数)`・`monocs_core_wait(コア)`。

例: `/usr/share/samples/primes_pthread.c`・`primes_omp.c`・`primes_mc.c`（実機で 1・2・3 コア 1155・714・497ms）。

## 6.7 Linux のソフトを動かす

Linux 用のソースと Makefile を、変えずにフォルダごと `/root/apps/名前/` に置いて動かせることを目指しています。
今は次のものが動きます（ソースは実機にだけ置いてあります）。

| ソフト | 動かし方 | メモ |
|---|---|---|
| mi（エディタ） | `mi FILE` | ユーザーのもの |
| fd（ファイルマネージャー） | `fd [DIR]` | ユーザーのもの |
| Lua 5.4.9 | `make posix` の後 `lua` | 公式テストが通る |
| SQLite 3.54.1 | `sqlite3 FILE.db` | 初回のコンパイルは約 12 秒 |
| vim 9.2 | `vim FILE` | 初回のコンパイルは数十秒（進み具合を表示する） |
| QuickJS | `qjs FILE.js` | 公式テストのほとんどが通る |

Pi 5 のフォルダから送るのは `sh tools/apps/push.sh ~/dev/tools/NAME` です。
足りない関数が出たら OS に足していきます（どうやったかの記録は `CLAUDE.md` の各ソフトの項）。

## 6.8 コンパイルのキャッシュ

`run`・名前で動かす・`make` のどれも、**2 回目からはキャッシュから動きます**（`run -lpwm servo.c` のようにライブラリを使うときも同じ）。

- **1 回目**: プログラムの .c と、使うライブラリ（`/usr/lib/pwm` の .c など）をコンパイルし、結果を `/var/cache/slimcc` に覚えます（電源を切っても残る）。
- **2 回目から**: ソース・読んだヘッダー・オプションが前と同じなら、コンパイルせずに読み込むだけです。前につないだ結果もメモリに覚えているので、
  同じ起動の間はそれをそのまま使い、もっと速くなります。

コンパイルし直すのは次のときだけです。

| 変えたこと | どうなるか |
|---|---|
| .c か、読んでいるヘッダーを書き換えた | 変わったファイルだけコンパイルし直す（ライブラリの分はそのまま） |
| オプションを変えた（`-DDEBUG` を足すなど） | 別のものとしてもう一度コンパイルする |
| カーネルを入れ替えて、中のコンパイラが変わった | 全部作り直す（最初の 1 回だけ） |

- ライブラリの分はライブラリ自身のオプションでコンパイルするので、同じライブラリを使うほかのプログラムとキャッシュを共有します。
- `cache` で量と使えた回数、`time run …` で速さを比べられます。消すのは `cache clear 名前`（そのプログラムだけ）・`cache clear`（全部）。

## 6.9 GCC との速さの違い

Monocs のコンパイラ（slimcc）が出すコードは、GCC（-O2）より遅いことがあります。ただし、差はプログラムの種類で大きく変わります。
「1.5 倍」は差の大きい種類のプログラムでの数字です。

| プログラム | 中身 | slimcc ÷ GCC |
|---|---|---|
| primes（Pi 5） | 整数のループと配列 | 約 1.05 倍 |
| strhash（Pi 5） | 文字列のハッシュ | 約 1.04 倍 |
| nbody（Pi 5） | 浮動小数点の計算 | 約 1.33 倍 |
| カーネルの中のコンパイラ（実機） | 大きく複雑な関数がたくさん | 約 1.45〜1.5 倍 |
| QuickJS（インタプリタ） | 巨大な 1 つの関数 | もっと開く |

- **差が出にくいもの**: 単純なループ・配列・文字列の処理（5% ほど）。サーボやセンサーのように**待っている時間が長いプログラム**
  （`servo.c` は時間のほとんどが `timer_delay_us` の待ちなので、どちらでも同じ動き）。ファイルやネットワークが中心のもの（SD カードや通信の速さで決まる）。
- **差が出やすいもの**: 浮動小数点の計算が多いもの（GCC はベクトル化や積和をうまく使う）。大きな関数に変数がたくさんあるもの
  （レジスタに収まらない値をメモリに逃がす分）。

電子工作や小さな道具なら気にしなくて大丈夫です。重い計算で気になったら `time` で測ってみてください。差を縮める作業の記録は `docs/slimcc-codegen.md` にあります。

## 6.10 速さの目安（実機）

| もの | 時間 |
|---|---|
| 1 つの小さな .c の初回のコンパイル | 0.1 秒前後 |
| mi（38 ファイル）の初回 | 約 1.2 秒（3 コアで分担） |
| キャッシュから動かす小さなコマンド | 0.01〜0.03 秒 |
| `primes.c`（ふるい） | 44ms |

速さを調べるときは、シェルの `time コマンド`、`perf コマンド`、`perf record コマンド`（どの関数か）を使います（[第 11 章](11-troubleshooting.md)）。
